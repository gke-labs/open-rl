Architectural Findings & Core Executive Insights
Why weight synchronization mechanism is the primary bottleneck in distributed LLM Reinforcement Learning

In distributed RL (e.g., PPO or GRPO), weight synchronization between dedicated gradient calculation nodes (Trainers) and high-throughput rollout generation nodes (Samplers) happens every single iteration. When training an 8.19 Billion parameter model (`Qwen/Qwen3-8B`), raw parameter weights consume roughly 16.0 GB across five safetensors shard files.

The IO Contention Disaster (Full Weight Sync): Under Full Weight Sync, the Trainer dumps all 16 GB onto shared NFS storage every step, taking up to 133.5s. When the vLLM Sampler acquires the physical GPU lock on shared Node #1 (`r8f5`), it spends 120.0s to 172.4s solely reading 16 GB from NFS into GPU memory before executing its 50-second rollout generation. If a rival job (`job-b`) requests the GPU during this window, it blocks inside SingleNodeTimeSlicer.acquire() for nearly 3 minutes—causing massive latency spikes (`time/sampling = ~212s`).

The Delta Snapshot Breakthrough (Delta Weight Sync): By patching only parameters whose update magnitude exceeds 0.01 (just 2.67% to 12.91% of the model / ~218 MB to 1.05 GB), checkpoint transmission drops to 5.3s – 6.89s. Inside the inference worker, DeltaSnapshotEngine applies 1D sparse tensor patches directly to a pinned CPU memory snapshot and transfers only modified tensors to GPU memory in 1.94s to 5.17s (a 65× speedup). When both concurrent jobs run Delta Sync (`Campaign 2`), queue starvation is completely eliminated, locking step times shoulder-to-shoulder at an optimal ~104 seconds.
